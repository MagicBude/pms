# 真实项目切片映射与复核

状态：业务已确认，隔离对账通过

## 1. 目的与数据边界

本批从 Git 忽略的 `production_requirements` 原始包中选择一个真实的“项目编号 + 旧请购单号”
组合，映射为项目、BOM、投产和生产请购完整链。规范包和 HTML 复核页含真实业务信息，只保存在
`.internal/migration/`，不得提交 Git、复制到测试夹具或粘贴到普通日志。

跟踪文档只记录聚合结论、规则和验证结果，不记录客户、项目、物料名称等业务值。

## 2. 源码确认与映射规则

- **源码确认**：原始数据共 1,616 行、51 个项目、318 个“项目 + 旧请购号”组合；旧请购号是
  一次生产请购的稳定分组边界，不能把整个项目误合成一张请购单。
- **源码确认**：1,593 行满足 `投产数量 = 单台数量 × 投产台数`，19 行不一致，4 行不可解析；
  自动候选只接受等式成立且数量为正的组合。
- **源码确认**：旧“投产单位”在全部 1,616 行中是同一个组织名称，不是“台、套”等数量单位。
- **合理推断**：旧数据集已经是带请购号的生产请购/外协需求，因此候选中的“加工件”和“采购件”
  都进入新系统生产请购；零件属性继续独立保存，供后续采购与外协分流。
- **优化建议**：新投产批次暂用“台”作为数量单位；旧投产单位原值只在复核页中展示，不写入
  计量单位字段。

候选还必须满足：项目编号可稳定迁移、销售订单客户可与客户主数据精确匹配、项目及请购级字段
一致、日期有效、物料身份不冲突。为便于逐行人工复核，本批限制为 5 至 12 行；最终只有一个
10 行组合满足全部条件，因此选择过程是确定性的，不依赖人工挑值。

## 3. 版本和保护机制

`pms-legacy-slice-v2` 在 v1 基础上增加：

- BOM 原始行号、层级路径、部套代号和部套名称；
- 物料零件属性；
- `business_pending` 样例状态。

`business_pending` 默认被 `migrate_legacy_slice` 拒绝。只有显式传入
`--allow-business-pending`，且使用独立 `PMS_DATA_DIR` 时，才可用于技术复核；报告验收范围固定为
`BUSINESS_PENDING`。命令会硬拒绝仓库正式 `data/`，即使全部检查为 `MATCHED` 也不能关闭
`AC-S001-043`。

## 4. 隔离验证结果

- 映射生成 1 个项目、1 个 BOM、1 个投产批次、1 张生产请购和 10 条来源明细。
- 全新隔离 SQLite 成功导入，10 条 BOM 原始行号、部套字段、零件属性和请购来源均保留。
- 最终结构化报告的项目、主数据、BOM、投产和请购检查全部一致，验收范围仍是
  `BUSINESS_PENDING`。
- 正式 `data/` 未修改；该结果不代表业务使用者已经确认字段含义。

## 5. 业务复核结论

业务使用者于 2026-08-25 查看原工作簿和本机复核页，确认整体业务链可作为验收基线，并授权按
以下工程化口径处理：

1. 10 行同一请购号的实体需求作为项目 BOM、投产和生产请购案例。
2. 旧“投产单位”按组织名称处理，新投产数量单位使用“台”。
3. “加工件”和“采购件”均进入生产需求，后续按零件属性分流外协和采购。
4. 同项目另外 3 行物流/返工运费不并入 BOM，归类为项目关联的非物料服务/物流费用；备注保留，
   其中两个日期倒挂作为旧数据异常保留。

`AC-S001-043` 业务签收完成。正式 `data/` 仍未修改，签收证明的是迁移口径与新旧结果一致，
不代表真实数据已导入日常使用库。
