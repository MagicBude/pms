# ADR-0010：旧 PMS 单一总迁移包与双击导入

状态：已接受（2026-08-26，用户明确要求最终只操作一个或少量导入文件）

## 背景

旧 PMS 数据分散在项目、生产需求、采购订单、入库、销售、付款、发票、报销和附件目录中。工程
实现需要按模块提取、映射和对账，但最终使用者不应理解每个中间 JSON、命令参数或执行顺序。

直接把所有旧工作簿交给新系统运行会重新引入宏、路径、编码和版本风险；把十几个模块分别交付
又容易漏导、顺序错误或在不同电脑使用了不配套的版本。真实数据还包含供应商、价格、银行和附件，
不能进入 Git 或普通共享渠道。

## 决策

1. 最终用户交付物默认为一个 `pms-legacy-import-bundle-v1.zip` 和仓库根目录一个
   `PMS-导入全部旧数据.bat`。只有单文件超过文件系统或传输介质限制时，才生成带编号和总摘要的
   少量分卷；不得因为内部模块多就要求使用者逐个运行命令。
2. ZIP 只包含新迁移器生成的版本化规范 JSON、附件清单、复核结果和 `manifest.json`；不包含旧宏、
   可执行文件、密码、许可证私钥或注册机。
3. `manifest.json` 固定记录总包 schema、生成时间、原始数据集摘要、每个成员路径、大小、SHA-256、
   记录数、依赖顺序、敏感级别和业务签收状态。成员缺失、未知、重复、越界路径或摘要不一致均拒绝。
4. 模块内部继续保留独立 schema 和测试。总包只是编排与完整性边界，不把客户、订单、库存和财务
   混成一个不可维护的巨大 JSON。
5. 导入 BAT 自动定位仓库和总包，检查 uv/Python/依赖和服务停止状态，创建正式备份，再执行总包
   预检。使用者不需要输入项目路径或逐个模块命令。
6. 第一次导入必须先在新的隔离 SQLite 数据目录完成全部迁移、重复导入、对账和启动检查。隔离
   演练失败不修改日常 `data/`；成功后才提供“导入现有库”或“切换到新数据目录”的明确动作。
7. 对现有库导入按模块事务提交并记录迁移批次。前置全量预检必须先通过；运行中失败时，导入器
   报告已完成模块并引导从自动备份恢复，不允许静默留下无法识别的半批数据。
8. 同一总包在同一租户重复执行必须复用一致事实；业务键相同但内容或来源摘要不同则停止并报告，
   不能覆盖使用者后来在新系统中的修改。
9. 无法从旧证据唯一确定的客户、来源行、税务或金额进入一份总包复核清单。使用者只需集中确认
   一次；未签收项阻止对应模块正式切换，但不要求手工重录全部正常数据。
10. 总包与复核文件默认写入 `.internal/migration/`，由 Git 忽略。换电脑必须通过用户控制的加密
    磁盘、正式备份或其他受控方式转移；普通 ZIP 本身不被描述为加密保护。

## 备选方案

- 让使用者逐个导入 JSON：顺序和版本容易出错，拒绝作为最终交付方式。
- 直接读取全部旧工作簿：会把宏、格式漂移和路径依赖带入运行时，拒绝。
- 把真实总包提交 Git：包含业务和可能的敏感数据，拒绝。
- 发现异常时自动创建“未知客户/未知物料”：制造虚假来源并污染后续财务，拒绝。
- 先改日常库再做对账：失败恢复成本高，拒绝；必须先隔离演练。

## 后果

- 内部仍会产生多个可测试的规范包，但使用者最终只面对一个 ZIP 和一个 BAT。
- 总包生成必须等待目标模块具备数据模型和导入器；尚未实现的库存、销售或财务数据不会被伪装成
  已导入。
- 总包可能包含大量真实数据和附件，移动与保管责任等同正式业务备份。
- 每次旧源数据或签收结论变化都生成新总包，不覆盖已用于演练或正式切换的旧版本。
