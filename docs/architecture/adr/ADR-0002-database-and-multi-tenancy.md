# ADR-0002 数据库兼容与多租户

状态：提议
日期：2026-08-23

## 背景

PMS 需要在本机单用户阶段使用零运维的 SQLite，并在内网多人和云端阶段使用 PostgreSQL。系统还要从第一天保留租户边界，避免商业化时重写全部表、查询和权限。

SQLite 官方适合设备本地、低写并发场景，但一个数据库文件同一时刻只能有一个写入者，也不建议让多台电脑通过网络文件系统直接访问。Django 官方在生产环境推荐 PostgreSQL，同时正式支持 SQLite。

## 决策

### 1. 数据库选择

- 本机单用户版使用 SQLite，数据库文件只由本机 PMS 服务进程访问。
- 内网多人版从第一个正式多人部署开始使用 PostgreSQL 18 的最新补丁版本。
- 云端版使用托管或自运维 PostgreSQL 18，并遵守供应商备份和升级策略。
- 禁止把 SQLite 文件放到共享盘供多台电脑或多个应用进程直接打开。
- 开发和自动化测试同时覆盖 SQLite 与 PostgreSQL，不能到内网阶段才首次验证兼容性。

### 2. 迁移与兼容子集

- 所有结构变化使用 Django migrations，禁止手工修改任何运行数据库结构。
- 迁移文件提交 Git，并从空库、已有版本升级和代表性数据三个路径测试。
- 核心模型只使用 Django 在 SQLite 和 PostgreSQL 上语义一致的字段、约束和查询。
- PostgreSQL 专属字段、扩展、触发器、部分索引或原始 SQL必须先有 ADR，并提供 SQLite 等价策略或明确限定部署形态。
- 不依赖 SQLite 宽松类型、大小写碰巧一致、隐式日期转换或未指定排序。

### 3. 租户模型

- 云端采用共享数据库、共享 schema、业务表显式 `tenant_id` 的模型。
- 本机版初始化一个默认租户，仍使用相同字段和约束。
- 用户通过 `membership` 加入租户；角色和对象范围属于成员关系。
- 不采用每租户一个数据库或每租户一个 schema 作为默认方案。
- 平台运营级跨租户访问不属于 P0；租户管理员也不能越过当前租户。

### 4. 租户隔离防线

每个请求按以下顺序建立边界：

1. Django 会话得到已认证用户；
2. 服务端解析当前成员关系和租户，忽略客户端任意传入的租户归属；
3. 应用服务显式接收 `TenantContext`；
4. 查询接口默认按租户过滤，并继续检查对象范围权限；
5. 外键关系和唯一约束在可能时包含租户；
6. 测试覆盖列表、直接 ID、更新、删除、附件和导出等跨租户反向场景。

禁止使用进程全局变量或线程不安全的隐式全局租户。中间件可以解析上下文，但应用服务仍需显式参数。

PostgreSQL Row-Level Security 可以在云端作为纵深防御，但不属于 P0 的唯一安全保障；引入前另写 ADR，避免 SQLite 与 PostgreSQL 行为不一致。

### 5. 主键与业务编号

- 核心租户级实体使用 UUIDv7 内部主键；Python 3.14 标准库负责生成，数据库只存储和约束。
- 用户可读的项目编号、请购单号等使用独立字段，唯一范围明确包含租户。
- 不向浏览器暴露连续数据库自增数作为安全边界。
- `SLICE-001` 请购号使用租户、业务类型和业务日期维度的序列表，在短事务内原子更新；允许安全产生的序号缺口。

### 6. 数据类型

- 金额使用定点十进制并显式记录币种；禁止二进制浮点保存金额。
- 数量使用定点十进制，投产台数等明确为整数的概念单独使用整数。
- 时间保存为 UTC 的带时区时间，按租户时区显示；业务日期单独使用日期类型。
- 状态使用稳定短代码并由应用状态机控制。
- JSON 只保存非核心扩展元数据、原始导入片段或审计摘要，不把关键可查询字段藏入 JSON。
- 文本比较和唯一性先做明确规范化，不依赖数据库默认排序规则碰巧一致。

### 7. 事务与并发

- Django 保持默认 autocommit；改变业务状态的应用用例显式使用短 `atomic()` 事务。
- 不把全部 HTTP 请求包装成长事务。
- 请购提交在同一事务内校验来源、计算剩余数量、生成编号、保存行和审计。
- 数据库唯一约束是防重复的最后防线，界面禁用按钮不能替代约束。
- 捕获完整性错误时在 `atomic()` 边界外处理，避免继续使用已经失败的事务。
- 缓存、文件移动和通知等动作使用提交后回调或可补偿流程，不能先宣告成功再等待数据库提交。

### 8. 数据所有权与删除

- 模块拥有自己的迁移和写入权，见 [模块边界](../module-boundaries.md)。
- 正式业务记录默认不物理删除，以状态和取消原因保留历史。
- 主数据停用不能破坏历史单据快照。
- 需要清理个人信息或附件时采用明确保留策略和审计，不直接级联删除整条业务链。

## 备选方案

### 全阶段只用 PostgreSQL

一致性最高，但本机试用需要安装和维护数据库服务，不符合最初的低门槛目标。

### 内网继续使用 SQLite

单一应用进程和低写入量时可能工作，但多人正式部署的并发、恢复和运维风险不值得节省 PostgreSQL 部署成本，因此不采用。

### 每租户独立数据库

隔离强，但迁移、连接池、运维和跨租户版本管理复杂，不适合产品早期。

### 每租户独立 schema

隔离比共享表明显，但 Django 默认迁移和第三方生态支持更复杂。当前规模不需要。

### 只依赖应用查询过滤

实现简单，但任何漏过滤都会泄露数据。必须同时使用显式上下文、查询封装、约束、权限和反向测试。

## 后果

### 正面

- 本机部署保持轻量，内网和云端获得正式并发数据库。
- 从第一天保留租户归属，减少商业化重构。
- 同一 ORM 与迁移降低两套持久化实现漂移。
- UUIDv7 兼顾不可猜测和索引局部性，不需要额外 ID 依赖。

### 代价

- 每个查询、唯一约束和测试都必须考虑租户。
- SQLite/PostgreSQL 双测试矩阵增加 CI 时间。
- 为保持可移植性，需要克制 PostgreSQL 专属便利功能。
- 内网升级不只是复制 SQLite 文件，需要正式迁移、对账和切换流程。

## 数据库切换验收

- 从空 SQLite 和空 PostgreSQL 均可执行完整迁移。
- 同一领域测试在两种数据库通过。
- SQLite 导出到 PostgreSQL 的演练报告包含记录数、关键数量、状态和附件清单对账。
- 切换过程先备份、停止写入、迁移、对账，再开放多人访问。
- 回滚方案明确数据回流或只读窗口，不能简单把旧 SQLite 重新开放写入。

## 复审条件

- SQLite 本机版出现经过测量且无法接受的锁等待或数据规模问题。
- 云端租户规模、合规或大客户隔离要求推动 schema/数据库级隔离。
- 必须使用 PostgreSQL RLS、全文检索或其他专属能力。
- PostgreSQL 18 接近支持结束。
