# ADR-0004 本机、内网与云端部署形态

状态：提议
日期：2026-08-23

## 背景

PMS 的演进目标是：最初在一台电脑通过 localhost 使用，随后部署到公司服务机供多人访问，成熟后通过域名向多家公司提供服务。三种形态必须共享业务代码，不能发展成三个分支产品。

部署差异应集中在数据库、附件、监听地址、TLS、进程管理、备份和监控等基础设施层。Django 的开发服务器不适合作为可交付运行服务器，因此本机版也需要正式应用服务器和启动器。

## 决策

### 1. 单一制品与配置档案

- 同一源码、迁移和测试生成同一应用制品。
- 通过 `local`、`lan`、`cloud` 配置档案选择基础设施，不使用长期代码分支区分版本。
- 配置有明确 schema，启动时验证；未知项、缺失密钥或不安全组合立即失败。
- 非敏感默认值进入仓库，密码、密钥和连接串通过环境或受保护配置注入。
- 每次启动暴露应用版本、迁移版本和配置档案，但不泄露秘密。

### 2. 本机版

| 项目 | 决策 |
| --- | --- |
| 访问 | Uvicorn 单进程监听 `127.0.0.1`，不监听所有网卡 |
| 数据库 | 应用私有数据目录中的 SQLite |
| 附件 | 应用私有数据目录中的本地存储 |
| 身份 | 首次启动引导创建默认租户和有密码管理员 |
| 启动器 | 检查数据目录、迁移和健康状态后启动服务并打开默认浏览器 |
| TLS | loopback 首版不强制 TLS；禁止把该档案改为局域网监听 |
| 进程 | 单应用进程、单 worker；同一数据目录禁止重复实例 |
| 备份 | SQLite 一致性备份、附件清单和配置版本组成一个备份集 |

开发模式和本机交付模式分开。开发者可使用自动重载；交付版不得启用 `DEBUG` 或 `runserver`。

### 3. 内网多人版

| 项目 | 决策 |
| --- | --- |
| 访问 | 用户只访问公司域名或服务机地址，不接触数据库文件 |
| 入口 | 反向代理终止 HTTPS，再转发到 Uvicorn 应用进程 |
| 数据库 | PostgreSQL 18，不使用网络共享 SQLite |
| 附件 | 仅 PMS 服务进程访问的服务机存储卷 |
| 进程 | 由操作系统服务或容器平台监管和自动重启 |
| 参考部署 | Linux 服务机上的容器化部署作为首选可重复路径 |
| 备份 | PostgreSQL 备份、附件快照和清单；定期恢复演练 |
| 监控 | 健康检查、结构化日志、磁盘/数据库容量和备份结果告警 |

如果公司必须使用 Windows 服务机，应另写经过测试的 Windows 服务部署说明；不能把开发电脑常驻窗口当作正式服务方案。

### 4. 云端版

| 项目 | 决策 |
| --- | --- |
| 访问 | 正式域名、强制 HTTPS、安全响应头和受控代理 |
| 数据库 | 托管或高可用 PostgreSQL 18 |
| 附件 | 对象存储，按租户键和权限访问 |
| 应用 | 不保存本地业务状态的容器实例，可水平扩展 |
| 秘密 | 云端秘密管理服务或等价受控机制 |
| 监控 | 集中日志、指标、错误跟踪、审计和告警 |
| 备份 | 数据库时间点恢复、对象版本/备份和跨故障域策略 |
| 商业能力 | 租户、套餐、订阅、权益和客户生命周期 |

云端可以增加适配器和运维能力，但不能绕开共享领域规则和租户测试。

### 5. 升级流程

每种档案遵循同一顺序：

1. 验证目标版本、兼容范围和可用磁盘；
2. 创建并验证数据库与附件备份；
3. 停止或排空写入；
4. 安装新制品并执行迁移；
5. 运行 system checks、健康检查和关键烟雾测试；
6. 恢复访问并持续观察；
7. 记录版本、迁移、操作者、结果和回滚窗口。

迁移发生后不能假设仅回滚应用二进制就能安全回档。每个版本必须说明数据库向后兼容或数据恢复方案。

### 6. 本机到内网迁移

```text
停止本机写入
   ↓
生成带版本与摘要的导出包
   ↓
在临时 PostgreSQL 执行迁移和导入
   ↓
对账租户、记录数、项目、BOM、数量、状态和附件摘要
   ↓
冻结旧 SQLite 为只读归档
   ↓
开放内网服务并执行验收
```

迁移不是把 SQLite 文件复制到共享盘。失败时保留旧系统只读证据，修复后重新执行可重复导入。

### 7. 健康检查

- `live`：进程能够响应，不访问外部依赖。
- `ready`：数据库迁移版本正确，数据库和必要存储可用，应用可以接收业务请求。
- 健康响应不包含路径、连接串、堆栈或秘密。
- 本机启动器只有在 `ready` 成功后打开浏览器。

### 8. 备份与恢复

- 备份只有经过恢复验证才算有效。
- 每个备份集记录应用版本、迁移版本、数据库、附件清单、时间和结果。
- 本机备份默认保存到用户选择的另一物理位置；不能只复制到同一数据目录。
- 内网和云端定义恢复点目标与恢复时间目标后再确定频率，首版不能编造没有演练的数据。
- 恢复到空环境后运行完整性和代表性业务检查。

## 备选方案

### 三套独立代码

短期可以分别优化，但业务规则、修复和迁移会快速漂移，故不采用。

### 所有形态都使用 Docker

内网和云端适合，但本机初学者需要额外安装和维护容器运行时，不符合低门槛目标。

### 所有形态都原生安装

本机简单，但内网和云端的依赖、升级和回滚难以重复。采用本机原生、服务器容器化的参考路径。

### 内网使用 SQLite 共享盘

部署看似简单，但违反 SQLite 官方对网络多客户端与并发写入的建议，故明确禁止。

## 后果

### 正面

- 单一业务代码可以沿三阶段演进。
- 本机保持低门槛，内网和云端采用适合并发的基础设施。
- 升级、备份和健康检查从第一版形成统一概念。
- 明确参考部署减少“每台机器手工配一次”的漂移。

### 代价

- 需要维护多配置档案和 SQLite/PostgreSQL 测试矩阵。
- 本机启动器、服务器容器和云端基础设施仍是不同交付包装。
- 从本机迁移到内网需要正式导出、导入和对账工具。
- Windows 服务机支持如果成为硬需求，需要额外验证和文档。

## 复审条件

- 本机用户无法接受 Python 运行时或原生包装体积。
- 公司服务机只能使用 Windows，且 Linux 容器参考部署不可行。
- 云端规模需要编排平台、多区域或独立租户资源。
- 监管要求改变 TLS、数据驻留、备份或灾备策略。
