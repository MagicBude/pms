# 本机版本升级与回退

状态：Phase 2 已验证基线

## 1. 边界

本流程适用于源码交付阶段的 `local + SQLite + 本地附件`。升级数据库结构只能向前执行 Django
迁移；不能用 Git 回退代码后继续打开已升级数据库，也不能人工删除迁移记录。

升级必须保留“旧代码 + 升级前已验证备份 + 新代码”三个可追踪点。备份恢复只支持创建空目录，
所以回退通过旧版本代码启动恢复目录实现，不覆盖原目录。

## 2. 升级前

1. 通知使用者停止录入并正常关闭本机 PMS。
2. 记录当前 `git rev-parse HEAD` 和 Python/uv 版本。
3. 按[本机备份与恢复](local-backup-restore.md)创建并验证备份，复制到当前数据目录之外。
4. 确认工作树干净；本地未提交源码不能作为可恢复发布版本。
5. 阅读目标版本 `CHANGELOG.md`、迁移说明和依赖变更。

## 3. 执行升级

取得目标提交后，在仓库根目录执行：

```powershell
uv sync --locked --all-groups
uv run python manage.py migrate --noinput
uv run python manage.py initialize_pms
uv run python manage.py check
uv run python manage.py launch_local --no-browser
```

重复初始化只同步稳定权限与默认角色矩阵，不重置管理员密码。启动后检查 `/health/ready`，再使用
浏览器验证登录、代表性项目、BOM 来源附件、投产和请购编号。确认前保留升级前数据目录和备份。

## 4. 失败处理与回退

- `uv sync` 失败：不要迁移，修复依赖或回到旧提交。
- `migrate` 失败：停止操作，保存完整错误和当前数据目录副本；不要手改表或迁移记录。
- ready 或业务检查失败：停止新版本，从升级前备份恢复到新的空目录。
- 使用记录的旧提交与其锁文件，在另一个干净仓库/工作树指向恢复目录启动验证。
- 只有旧版本 ready、登录和代表性业务链都通过后，才把恢复目录作为回退候选。

任何回退都不能让旧代码直接打开已经由新版本迁移过的数据库。若新版本产生了升级后的新录入，
回退会丢失该窗口数据，必须先由业务负责人决定停机、导出或接受损失。

## 5. Phase 2 演练口径

Phase 2 在隔离目录执行旧提交安装、当前提交依赖同步与迁移、重复初始化、受控业务样例导入、正式
启动、备份、离线验证、空目录恢复和恢复目录再次启动。演练目录、虚构数据和临时密码不进入 Git；
工作日志只记录提交、计数和结果，不记录秘密或绝对临时路径。
