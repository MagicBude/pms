# 权限与审计基线

状态：已验证（SQLite 本地与 PostgreSQL 18 CI）

## 1. 目的与边界

本基线把[已接受的角色权限矩阵](../product/role-permission-matrix.md)落实为框架无关的
稳定权限代码、默认角色授权和追加式审计端口。它解决“谁能对哪个租户内的什么对象
执行什么动作”以及“重要动作留下哪些最小证据”，不提供登录页面、角色管理页面或
业务对象关系查询。

浏览器不能自行决定权限。隐藏按钮只改善体验，应用服务仍必须使用可信
`TenantContext`、稳定权限代码和服务端对象关系完成授权。

## 2. 授权计算顺序

授权采用默认拒绝，固定顺序如下：

1. 先比较目标对象的 `tenant_id` 与可信上下文；不同租户立即拒绝；
2. 按当前 `membership_id` 聚合全部角色对目标权限的授权；
3. 没有明确授权则拒绝；
4. `tenant` 范围允许访问当前租户内对象；
5. `related` 范围还要求调用方通过可信服务端查询证明成员与对象相关。

`tenant_admin` 也不能越过第一步。调用方不能直接把请求参数解释为“相关”；项目、
BOM 等模块建立后，应从当前成员与业务对象的服务端关系计算该事实。

授权查询每次都会检查 membership 和 tenant 的启用状态并读取当前角色关系。因此停用
成员、停用租户或解除角色后，仍持有旧上下文的请求也不能继续沿用旧权限。

## 3. 权限和角色数据

- `PermissionCode` 是业务代码唯一使用的稳定能力代码；
- `RoleCode` 和 `DEFAULT_ROLE_GRANTS` 是已接受矩阵的可执行默认配置；
- 角色只是权限组合，业务代码不能判断角色名称；
- 一个 membership 可以拥有多个角色；同一权限取较宽的 `tenant` 范围；
- `Permission`、`Role`、`RolePermission` 和 `MembershipRole` 建立持久化结构；
- F-006 迁移不写默认数据，F-009 将从可执行矩阵幂等初始化本机默认租户和管理员。

## 4. 审计事件

应用层通过 `AuditRecorder` 追加事件。每条记录包含：

- 租户、可选操作者和可选 membership；
- 稳定动作、对象类型和对象标识；
- `success`、`denied` 或 `failure` 结果；
- 自动生成的带时区发生时间；
- 仅含必要业务差异的结构化摘要。

摘要会递归检查字段名，拒绝密码、令牌、会话、Cookie、Authorization、secret、附件
正文和文件内容类字段；错误只指出字段路径，不回显字段值。完整外部输入不能进入摘要。

## 5. 追加式保证与限制

`AuditLog` 不暴露更新或删除服务，模型实例和 QuerySet 的常规更新、删除路径都会拒绝。
这能阻止应用代码意外覆盖证据，但不能代替数据库管理员权限控制：拥有底层数据库维护
权限的人仍可能直接改表。生产部署还必须使用最小数据库账号、备份、访问监控和恢复演练。

审计表对 tenant 使用保护删除；actor 和 membership 可在主体清理后置空，使历史动作
仍可保留。反向迁移会删除审计证据，只允许在未承载真实数据的开发环境使用。

## 6. 当前非目标

- 默认角色和权限数据初始化（F-009）；
- 登录、退出和业务状态迁移的具体审计调用点；
- 项目、BOM、投产和请购的“相关对象”查询；
- 审计查询页面、导出、留存周期和防篡改外部归档；
- 跨租户平台运营权限。

后续用例必须同时覆盖允许、无权限、对象范围不足和跨租户场景；重要成功、失败与拒绝
路径必须通过同一审计端口记录。
