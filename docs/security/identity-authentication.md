# 身份与认证基线

状态：F-004 基线

## 1. 边界

`identity.User` 表示能够登录 PMS 的全局身份，不表示用户属于哪个企业，也不直接保存租户角色。用户与租户之间的 membership、启用状态和角色由 F-005 建立，从而避免一个用户加入多家公司时复制账号或混淆权限。

其他 Django 模块只能通过 `settings.AUTH_USER_MODEL`、`get_user_model()` 或迁移中的动态依赖引用用户，禁止直接依赖模型物理路径。

## 2. 登录标识

- 首版使用全局唯一的 `username` 登录，符合已接受的 P0“基础用户名/密码登录”范围；
- 用户名沿用 Django 的 Unicode 用户名验证和 150 字符上限；
- `email` 当前可选且不唯一，不作为登录标识；
- 若未来改为邮箱、手机或企业域账号登录，必须先评审唯一性、找回、验证和历史数据迁移。

## 3. 标识与状态

- 用户主键使用 Python 3.14 生成的 UUIDv7，与业务可见用户名分离；
- `is_active=False` 表示账号停用，Django 默认认证后端即使密码正确也拒绝认证；
- 不物理删除已经参与业务或审计的用户；具体个人信息保留和匿名化规则后续制定；
- `is_staff` 和 `is_superuser` 属于受控运维能力，不等于租户管理员，也不能绕过租户边界。

## 4. 密码与会话

- 密码只通过 Django 用户管理器和密码 API 设置，数据库保存成熟哈希格式，不保存明文；
- 启用 Django 默认密码强度校验器，具体创建入口必须显式调用验证；
- 启用 auth、contenttypes、sessions 和认证中间件，但 F-004 尚未提供登录页面、退出页面或 Django Admin；
- 后续登录入口必须加入速率限制、安全错误提示以及成功、失败和退出审计；
- 停用账号后，新认证立即失败；已有会话的主动失效策略必须在正式登录页面交付前实现并测试。

## 5. 首次迁移

`identity.0001_initial` 是 PMS 的第一次自有迁移。它依赖 Django auth 的权限定义，但通过 `AUTH_USER_MODEL` 创建 `identity_user`，不会创建默认 `auth_user`。从空 SQLite 和 PostgreSQL 18 执行相同迁移历史。

本阶段没有旧用户数据可回填。迁移反向操作会删除用户表，只适用于尚未承载真实数据的开发环境；生产环境不得用简单反向迁移替代备份恢复方案。

## 6. 当前非目标

- 登录和退出 UI；
- 邮箱验证、找回密码和多因素认证；
- 单点登录或企业目录集成；
- 租户成员、角色和权限；
- 登录审计、速率限制和会话强制失效；
- Django Admin 运维入口。

上述能力必须在对应批次独立设计、测试和记录，不能因为 Django 已提供部分默认组件就默认启用。
