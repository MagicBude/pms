# 注释规范

状态：已接受

## 1. 目标

PMS 的注释采用“教材级解释”标准：读者不仅能知道代码做了什么，还能理解业务背景、设计原因、边界条件、数据单位、异常策略和取舍。

教材级不等于逐行翻译语法。好的注释补充代码无法自然表达的信息；明显、重复或过期的注释会降低学习质量。

## 2. 注释的四个层次

### 2.1 模块注释

核心模块应说明：

- 模块负责的业务能力；
- 不负责什么；
- 主要输入和输出；
- 依赖哪些抽象；
- 重要不变量；
- 与其他模块的协作方式。

### 2.2 类型和公共接口注释

公共类、协议、接口、值对象和 DTO 应说明：

- 业务含义；
- 生命周期；
- 字段含义和单位；
- 创建条件和不变量；
- 可见副作用；
- 可能的失败。

### 2.3 函数注释

公共函数、核心领域函数和复杂私有函数应说明：

- 为什么需要该操作；
- 参数的业务含义，而不是只重复类型；
- 返回值代表什么；
- 抛出或返回哪些错误以及何时发生；
- 是否修改状态、写数据库、写文件或调用外部系统；
- 幂等性、事务和权限要求；
- 非直观边界和示例。

### 2.4 行内注释

行内注释只用于解释局部无法由重命名或拆函数解决的内容，例如：

- 法规、合同或历史兼容规则；
- 非直观算法和公式；
- 特殊单位、精度或舍入；
- 并发、锁和事务原因；
- 性能优化及测量依据；
- 安全控制和租户隔离；
- 外部系统的已知限制。

## 3. 必须注释的内容

- 领域状态转换和不变量；
- 金额、税率、折扣、汇率和舍入规则；
- 编号生成和唯一性规则；
- 权限和跨租户管理逻辑；
- 数据迁移中的字段映射、清洗和兼容策略；
- 复杂 SQL、批处理和性能优化；
- 重试、幂等、锁和并发冲突处理；
- 通过临时方案规避外部缺陷的代码；
- 安全敏感操作；
- 难以从名称推断的单位和时间语义；
- 公开 API、可复用库和扩展点。

## 4. 不应出现的注释

### 4.1 复述代码

错误示例：

```python
# 给数量加一
quantity += 1
```

代码已经完整表达行为，注释没有增加知识。

### 4.2 为糟糕命名打补丁

错误示例：

```python
# 订单总金额
x = calculate(items)
```

应改成：

```python
order_total = calculate_order_total(items)
```

### 4.3 保留废弃代码

不使用大段注释保存旧实现。删除死代码，必要历史由 Git 和 ADR 保存。

### 4.4 无法验证的断言

避免“这里绝对不会失败”“临时处理一下”“应该没问题”等没有依据的描述。

### 4.5 过期路线图

未来工作应进入 issue、产品路线或正式 TODO，不能散落在长期无人维护的注释中。

## 5. 教材级写法

教材级注释应回答读者最可能提出的问题：

1. 这条规则来自哪里？
2. 为什么不采用更直观的写法？
3. 输入的单位和有效范围是什么？
4. 对事务、权限和租户有什么要求？
5. 失败后系统处于什么状态？
6. 哪些边界容易被忽略？
7. 修改它时必须同步修改什么测试或文档？

## 6. Python 文档注释示例

如果技术栈选择 Python，采用项目统一的 docstring 风格。以下示例使用结构化的中文说明和英文标识符：

```python
def confirm_purchase_order(
    command: ConfirmPurchaseOrder,
    actor: ActorContext,
) -> PurchaseOrder:
    """确认采购订单并冻结本次确认使用的价格快照。

    订单确认是采购流程的业务边界。确认后，订单明细不能继续跟随
    供应商最新报价自动变化，否则历史订单金额和后续付款对账会失真。

    Args:
        command: 待确认订单的标识和客户端看到的版本号。版本号用于
            检测其他用户已经修改订单的并发冲突。
        actor: 当前操作者及其可信租户上下文。tenant_id 必须来自
            服务端会话，不能采用客户端提交的任意值。

    Returns:
        已确认的采购订单。返回对象包含冻结后的含税金额和新版本号。

    Raises:
        OrderNotFoundError: 当前租户中不存在该订单。
        PermissionDeniedError: 操作者没有确认采购订单的权限。
        InvalidOrderStateError: 订单不是“草稿”状态或缺少有效明细。
        ConcurrentUpdateError: 数据库版本与 command 中的版本不一致。

    Side Effects:
        在同一数据库事务中更新订单状态、保存价格快照并写入审计日志。
        本函数不发送邮件；通知由事务提交后的事件处理器负责。
    """
```

重点在于解释价格快照、可信租户来源、并发控制和事务副作用，而不是逐字重复函数签名。

## 7. TypeScript 文档注释示例

如果技术栈包含 TypeScript，公开函数使用 TSDoc/JSDoc 可识别格式：

```typescript
/**
 * 将用户输入的含税单价转换为订单行的金额快照。
 *
 * 金额在订单确认时计算并冻结，后续供应商报价变化不能反向修改
 * 历史订单。所有参数均以订单币种的最小精度参与 Decimal 运算，
 * 禁止在这里转换为 JavaScript number。
 *
 * @param unitPrice - 含税单价；必须大于等于 0。
 * @param quantity - 采购数量；单位由物料行的 unit 字段定义。
 * @returns 未进行付款级舍入的订单行金额。
 * @throws DomainValidationError 当价格、数量或单位无效时抛出。
 */
export function calculateLineAmount(
  unitPrice: Decimal,
  quantity: Decimal,
): Decimal {
  // 舍入在订单汇总边界统一完成，避免逐行舍入产生累计误差。
  return unitPrice.mul(quantity);
}
```

## 8. 业务规则注释示例

较差写法：

```python
if paid_amount > order_total:
    raise ValueError("too much")
```

推荐写法：

```python
# 付款登记不能超过订单当前可付余额。这里比较“可付余额”而不是订单
# 总额，因为同一订单可能已经存在已确认付款或处于审批中的付款申请。
# 可付余额的计算口径见 docs/product/payment-rules.md。
if requested_amount > payable_balance:
    raise PaymentExceedsBalanceError(
        requested=requested_amount,
        available=payable_balance,
    )
```

如果注释引用尚不存在的规则文档，应在同一变更中创建文档或改为引用已有需求编号。

## 9. 算法和公式注释

公式注释至少说明：

- 业务名称；
- 变量单位；
- 精度和舍入位置；
- 异常输入；
- 依据或对照案例。

示例：

```python
# 未税金额 = 含税金额 / (1 + 税率)。税率使用小数形式，例如 13% 保存为
# Decimal("0.13")。按财务口径在单据总额层保留 2 位小数，明细中间结果
# 保留完整精度，防止多行订单产生累计舍入差异。
net_total = (gross_total / (Decimal("1") + tax_rate)).quantize(
    CENT,
    rounding=ROUND_HALF_UP,
)
```

## 10. TODO、FIXME 和临时措施

### TODO

只用于已明确但不属于当前变更范围的工作：

```text
TODO(PMS-1234, 2026-08-21): PostgreSQL 切换后改用数据库 advisory lock。
```

至少包含可追踪编号或责任信息以及原因。没有跟踪入口的长期 TODO 不应合并。

### FIXME

表示当前实现存在已知缺陷或风险，应关联缺陷记录：

```text
FIXME(PMS-1288): 当前旧数据缺少币种，迁移阶段暂按租户默认币种解释。
```

### 临时兼容代码

必须说明：

- 兼容对象；
- 为什么仍需要；
- 删除条件；
- 验证它的测试。

## 11. 数据库迁移注释

迁移文件应说明业务意图，尤其是数据回填和不可逆操作：

- 为什么新增或修改字段；
- 旧数据如何解释；
- 空值和异常记录如何处理；
- 是否会锁表或耗时；
- 回滚能够恢复什么，不能恢复什么；
- 迁移后的验证查询或计数。

## 12. 测试注释

测试名称优先表达场景，不用注释重复 Arrange/Act/Assert。以下情况需要测试注释：

- 业务案例来源不明显；
- 测试数据刻意选择边界值；
- 复现历史缺陷；
- 需要解释并发时序；
- 断言看似反直觉但符合业务规则。

## 13. 注释语言

- 业务解释和团队维护注释优先使用中文。
- 标识符、协议字段、错误码和技术专有名词保持英文。
- 引用外部标准时保留正式名称，并补充中文解释。
- 同一段注释不要无规则混用中英文标点和术语。

## 14. 注释维护

- 修改规则时同步修改代码、注释、测试和文档。
- 评审者必须验证注释描述的是当前行为，而不是原计划。
- 如果注释与代码冲突，视为缺陷；不能默认为代码一定正确。
- 重构后删除已经由清晰结构表达的冗余注释。
- 关键规则的完整说明进入文档，代码注释提供附近摘要和链接，避免复制两份容易漂移的长文。

## 15. 评审检查表

- 注释是否解释了“为什么”？
- 是否准确描述单位、边界、权限和副作用？
- 是否重复了明显代码？
- 是否掩盖了糟糕命名或过长函数？
- 是否含有真实个人数据、密码或秘密？
- 引用的文档和 issue 是否存在？
- 代码变化后注释是否仍然正确？
- 学习者能否从注释理解规则，但仍需要阅读代码本身？
