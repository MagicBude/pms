# 日志与异常规范

状态：已接受

## 1. 目标

错误处理需要同时服务用户、开发者和运维人员：用户得到可行动的说明，开发者得到可定位的上下文，系统不泄露敏感信息。

## 2. 错误分类

- 输入错误：格式、必填项或范围不合法。
- 业务规则错误：状态、余额、重复编号或业务前置条件不满足。
- 权限错误：未认证、无权限或租户范围不允许。
- 冲突错误：并发更新、重复提交或唯一约束冲突。
- 外部依赖错误：数据库、文件存储、邮件或第三方服务失败。
- 系统缺陷：未预期异常和不变量被破坏。

每类错误有稳定机器码。用户消息可本地化，错误码不能随意改变。

## 3. 异常处理

- 在最接近错误来源的位置补充安全上下文。
- 在系统边界将内部异常映射为用户或 API 错误。
- 不捕获后无处理地继续执行。
- 不用通用异常表示正常业务分支。
- 数据库唯一约束等底层错误应转换为明确业务冲突。
- 用户响应不包含堆栈、SQL、绝对路径、连接字符串或内部类型名。

## 4. 日志级别

- DEBUG：开发诊断细节，生产环境默认关闭或受控采样。
- INFO：关键业务里程碑和服务生命周期。
- WARNING：可恢复异常、降级、重试或即将达到限制。
- ERROR：操作失败，需要调查但服务仍可运行。
- CRITICAL：服务不可用、数据一致性或安全边界受到严重威胁。

## 5. 结构化字段

业务日志优先包含：

```text
timestamp
level
event
request_id / correlation_id
tenant_id
actor_id
operation
entity_type
entity_id
result
duration_ms
error_code
```

只记录定位问题所需字段。不要把完整业务对象序列化到日志。

## 6. 隐私与秘密

禁止记录：

- 密码、验证码、令牌、会话 Cookie；
- 授权签发私钥或许可证原文；
- 完整身份证号、银行卡号和银行凭证；
- 数据库连接字符串中的密码；
- 发票、合同、图纸或附件正文；
- 不必要的客户联系人信息。

必须记录敏感标识时，使用稳定内部 ID 或遮罩后的尾号。

## 7. 审计日志与运行日志

- 运行日志用于诊断系统行为，可以按保留策略轮转。
- 审计日志用于回答谁在何时对哪个业务对象做了什么，权限和保留策略更严格。
- 审计日志不能只依赖普通文本日志。
- 重要写操作即使失败也应记录尝试结果，但不能记录秘密输入。

## 8. 用户提示

用户错误提示应包含：

- 发生了什么；
- 用户可以采取什么行动；
- 必要时提供可向支持人员报告的 request_id；
- 不把内部实现细节推给用户。

示例：

```text
订单已被其他用户修改，请刷新后重新确认。
错误码：ORDER_VERSION_CONFLICT
请求编号：01J...
```
