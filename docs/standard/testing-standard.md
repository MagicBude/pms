# 测试规范

状态：已接受

## 1. 目标

测试用于证明业务规则和边界，不只是提高覆盖率数字。测试应当可重复、互相隔离、失败信息清晰，并作为学习者理解系统行为的可执行示例。

## 2. 测试分层

### 2.1 单元测试

- 测试领域规则、值对象、计算、状态转换和纯函数。
- 不访问网络、真实数据库、当前时间或随机全局状态。
- 使用显式注入的时钟、ID 生成器和外部接口。
- 运行快速，定位单一规则。

### 2.2 集成测试

- 测试 ORM 映射、数据库约束、事务、仓储和存储适配器。
- 数据库相关测试覆盖 SQLite 和 PostgreSQL 的关键差异。
- 每个测试独立创建或回滚数据，不能依赖执行顺序。
- 验证真实唯一约束、外键、并发和租户过滤。

### 2.3 API/界面测试

- 验证输入、权限、错误结构、序列化和状态码。
- 不用大量界面测试重复领域层所有组合。
- 重要页面覆盖加载、空状态、失败、无权限和成功交互。

### 2.4 验收测试

- 从用户业务场景出发验证端到端结果。
- 与旧系统对照的规则应记录旧系统入口、样本条件和预期差异。
- 不要求所有历史界面像素一致，重点验证业务结果和必要操作体验。

### 2.5 迁移测试

- 同一输入重复执行不得产生非预期重复记录。
- 验证源记录数、目标记录数、跳过数、错误数和金额等关键合计。
- 保留匿名化边界样本：空值、重复编号、非法日期、缺失附件和旧格式。

## 3. 测试场景

每条重要规则至少考虑：

- 正常成功；
- 最小值和最大值；
- 空值和缺失输入；
- 非法状态；
- 无权限；
- 其他租户；
- 重复提交；
- 并发修改；
- 下游失败和事务回滚；
- 时间、金额、单位和舍入边界。

## 4. 命名

测试名称描述场景和结果：

```text
test_confirm_order_freezes_supplier_price_snapshot
test_user_cannot_read_order_from_another_tenant
test_payment_rejects_amount_above_payable_balance
```

避免 `test_create_1`、`test_success` 等缺少业务含义的名称。

## 5. 测试结构

- Arrange：只准备当前行为需要的数据。
- Act：执行一个主要动作。
- Assert：断言业务结果和必要副作用。
- 一个测试可以有多个相关断言，但不应测试多个无关用例。
- 失败断言同时验证错误类型和关键上下文，不只验证任意异常发生。

## 6. 测试数据

- 默认使用工厂或构建器创建最小有效对象。
- 测试数据使用虚构名称，禁止复制真实客户和财务数据。
- 时间和随机值固定，避免偶发失败。
- 明确金额币种、单位、租户和用户身份。
- 快照测试只能用于稳定表现层输出，不能替代核心业务断言。

## 7. 缺陷修复

修复缺陷前先添加能够复现的测试，然后修改实现使测试通过。无法自动化复现时，应在变更说明中记录原因、手工验证步骤和后续自动化条件。

## 8. 覆盖率

覆盖率用于发现遗漏，不能替代场景设计。领域规则、租户隔离、权限、金额计算、迁移和授权验证属于高风险区域，应追求接近完整的分支覆盖和有意义的边界测试。

## 9. 测试完成标准

- 测试在干净环境可重复执行。
- 不依赖 `.internal/legacy-pms/` 或真实业务数据。
- 不访问未声明的外部网络。
- 并行执行时不互相污染。
- 失败消息能够定位业务规则。
- 新功能包含对应层级测试。
