# 文档规范

状态：已接受

## 1. 文档职责

- `product/` 说明做什么、为谁做和如何验收。
- `architecture/` 说明系统边界和技术决策。
- `deployment/` 说明如何安装、升级、备份和恢复。
- `development/` 说明如何开发、调试和发布。
- `standard/` 说明所有实现必须遵守的规则。
- `security/` 说明安全、权限、授权和隐私要求。
- `migration/` 说明旧系统知识和数据如何迁移。

## 2. 状态

重要文档在标题后标记：草案、评审中、已接受或已废弃。

- 草案不能被当作稳定契约。
- 已接受文档发生实质变化时，需要说明原因并评审影响。
- 已废弃文档保留替代文档链接和废弃原因。

## 3. 写作结构

复杂文档优先包含：

1. 目的；
2. 背景；
3. 范围与非范围；
4. 术语；
5. 规则或方案；
6. 示例；
7. 风险与边界；
8. 待决策事项；
9. 验收或检查方式。

## 4. 表达要求

- 先写结论，再写原因和细节。
- 一段只表达一个中心观点。
- 区分事实、假设、建议和决定。
- 使用明确主语，避免“需要处理一下”“适当优化”等无法验收的表达。
- 数值写明单位和统计口径。
- 示例不能使用真实客户、员工、银行或凭证数据。
- 命令和路径必须可复制，且说明运行目录和前置条件。

## 5. 链接和重复

- 规则只保留一个权威来源，其他文档使用链接引用。
- 不复制大段相同规则，避免多处版本漂移。
- 使用相对链接连接仓库内文档。
- 重命名文档时更新所有入站链接。

## 6. ADR

架构决策记录至少包含：

```text
# ADR-0001 标题

状态：提议 | 已接受 | 已替代 | 已废弃
日期：YYYY-MM-DD

## 背景
## 决策
## 备选方案
## 后果
## 复审条件
```

ADR 记录当时为什么做出决定，不能因为后续方案改变而重写历史。新决策通过新的 ADR 替代旧 ADR。

## 7. 代码与文档同步

以下变更必须同步文档：

- 产品范围、业务口径和状态流转；
- 公共 API；
- 数据库结构和迁移要求；
- 部署、配置和环境变量；
- 权限、租户和许可证；
- 开发命令和质量工具；
- 旧系统迁移规则。

## 8. 教学性

教学文档应包含动机、正确示例、反例、边界和验证方式。不要只给出“最佳实践”结论而不解释它解决了什么问题。
