# Git 规范

状态：已接受

## 1. 仓库边界

只提交新系统源码、测试、迁移、非敏感配置样例和文档。

禁止提交：

- `.internal/legacy-pms/`；
- 真实客户、供应商、员工和财务数据；
- 发票、凭证、合同、图纸和生产附件；
- 数据库文件、备份和运行日志；
- 密码、令牌、私钥和生产连接字符串；
- 构建产物、依赖目录和本机 IDE 文件。

## 2. 分支

- 默认分支保持可构建、可测试。
- 功能分支短生命周期并聚焦一个目标。
- Codex 创建分支时默认使用 `codex/` 前缀。
- 不在功能分支混入无关格式化、批量重命名或数据文件。

## 3. 提交

一个提交表达一个逻辑变更，并能够独立评审。

### 3.1 提交格式

提交信息使用以下结构：

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- `type` 必填，使用英文 Conventional Commits 类型；
- `scope` 原则上必填，使用下文 PMS 范围名；确实横跨整个仓库时使用 `repo`；
- `subject` 必填，使用中文祈使句，准确说明结果，不写“更新内容”“修改文件”等模糊描述；
- `body` 对非简单提交必填，至少说明动机、主要变更和实际验证；
- `footer` 用于关联 Issue、说明不兼容变更或其他追踪信息。

只有错别字、单行链接修正、纯格式调整等无需额外背景的简单提交可以省略正文。是否简单以变更风险和理解成本判断，而不是以文件数量判断。

### 3.2 类型

| 类型 | 适用场景 |
| --- | --- |
| `feat` | 新增对使用者有意义的功能 |
| `fix` | 修复缺陷或错误行为 |
| `docs` | 只修改文档或注释说明 |
| `style` | 不改变行为的格式调整 |
| `refactor` | 不新增功能、不修复缺陷的代码重构 |
| `perf` | 可验证的性能优化 |
| `test` | 新增或调整测试 |
| `build` | 构建系统、依赖或打包变化 |
| `ci` | 持续集成和自动化流程变化 |
| `chore` | 其他不改变产品行为的仓库维护 |
| `revert` | 回滚已有提交 |

不能因为 `chore` 含义宽泛就用它代替更准确的类型。

### 3.3 PMS scope

| 类别 | scope |
| --- | --- |
| 产品与需求 | `product` |
| 架构与 ADR | `architecture` |
| 部署与运维 | `deployment` |
| 开发流程 | `development` |
| 工程规范 | `standard` |
| 旧系统迁移 | `migration` |
| 安全与授权 | `security` |
| 平台业务模块 | `tenancy`、`identity`、`authorization`、`audit` |
| 核心业务模块 | `master-data`、`projects`、`attachments`、`bom`、`production`、`procurement` |
| 技术平台 | `platform` |
| 跨仓库范围 | `repo` |

新增稳定模块时同步维护本表。不要临时使用同义词造成历史难以筛选。

### 3.4 主题

- 使用现在时、祈使语气，例如“建立租户上下文”，不写“建立了租户上下文”；
- 中文主题建议不超过 50 个字符；
- 结尾不加句号；
- 表达可观察结果，不罗列文件名；
- 不使用 `update`、`changes`、“修复问题”等无法追踪含义的描述。

推荐示例：

```text
docs(architecture): 接受数据库与租户隔离决策
feat(procurement): 新增生产请购提交用例
fix(authorization): 阻止跨租户查询附件
test(production): 覆盖投产数量舍入边界
refactor(attachments): 隔离附件存储适配器
chore(repo): 配置静态检查
```

### 3.5 正文与页脚

非简单提交的正文建议使用以下小节；无对应内容的小节可以省略：

```text
动机：
- 说明为什么现在需要这次变更

主要变更：
- 说明关键设计和实现，不只重复文件名

验证：
- 列出实际执行的测试、检查和结果

影响：
- 说明兼容性、数据、部署、风险和后续动作
```

正文与 Header 之间空一行，每行尽量保持易读；不得写入密码、令牌、真实客户数据或不必要的本机绝对路径。没有运行的测试不能写成已经通过，应写明“尚未配置”或未运行原因。

关联任务使用 `Refs #123`，需要自动关闭的问题使用 `Closes #123`、`Fixes #123` 或 `Resolves #123`。不兼容变更必须使用：

```text
BREAKING CHANGE: 说明影响、旧行为、新行为和迁移办法
```

### 3.6 原子性与频率

生成代码和迁移应与产生它们的逻辑变更一起提交。文档、测试和实现共同表达同一个规则时属于同一逻辑变更，不应人为拆开；互不相关的清理、重构和新功能不得捆绑。

每个独立任务完成并通过相应验证后必须创建一次提交，形成可追溯、可回档的检查点。不能把下一个任务的半成品提前混入当前提交，也不能为了减少提交次数捆绑互不相关的变更。

仓库提供根目录 `.gitmessage` 模板。需要在本机编辑器中使用时可以执行：

```bash
git config --local commit.template .gitmessage
```

不强制每台电脑写入相同本地 Git 配置；AI 或自动化提交仍必须生成等价的完整信息。

## 4. 变更前检查

- 确认工作树已有改动的归属，不能覆盖用户无关修改。
- 检查 `.gitignore` 是否覆盖新生成数据。
- 涉及重大决策时先更新 ADR 或产品文档。
- 涉及数据库时确认迁移和回滚策略。

## 5. 提交前检查

- 查看完整 diff 和未跟踪文件。
- 使用精确文件列表暂存，禁止不检查就执行 `git add .`。
- 运行格式化、Lint、类型检查和受影响测试。
- 扫描秘密和真实数据。
- 确认注释、文档、迁移和测试同步。
- 确认 Header 的 type、scope、中文主题和正文符合本规范。
- 不使用 `--no-verify` 绕过正常质量门槛，除非有明确原因并记录。

## 6. 历史安全

- 不使用强制推送覆盖他人已共享历史，除非团队明确协调。
- 不使用破坏性重置处理不属于自己的改动。
- 如果秘密或敏感数据已经进入历史，删除工作树文件不够，必须执行密钥轮换和受控历史清理。

## 7. 评审

评审重点依次是：业务正确性、数据和租户安全、可恢复性、测试证据、可维护性和风格。

格式问题应尽量由自动化工具处理，人工评审集中于工具无法判断的设计和业务风险。
