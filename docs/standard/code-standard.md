# 代码规范

状态：已接受

## 1. 目标

代码应同时满足正确、清晰、可维护、可测试、安全和可教学。优先让下一位维护者能够准确理解和安全修改，而不是追求最少行数或展示复杂技巧。

## 2. 基本原则

### 2.1 先表达业务，再表达框架

- 使用业务语言命名类型和用例。
- 控制器、页面和 ORM 模型不是业务规则的最终归属。
- 核心规则应能脱离 Web、数据库和文件系统测试。

### 2.2 单一职责

- 一个模块只负责一个清晰的领域或技术职责。
- 一个函数只完成一个可以准确命名的动作。
- 当函数同时进行解析、校验、授权、持久化和通知时，应拆分为可组合步骤。
- 拆分不是追求极小函数；保持同一抽象层级比机械限制行数更重要。

### 2.3 显式优于隐式

- 重要业务规则、单位、时区、事务和权限边界必须显式。
- 避免依赖全局可变状态、隐式单例和导入时副作用。
- 避免通过文件名、目录名或界面文字推断关键业务状态。
- 默认参数不能隐藏安全或数据范围变化。

### 2.4 简单优先

- 默认采用模块化单体。
- 在有重复证据前，不提前建立复杂通用框架。
- 在有容量或可靠性证据前，不提前拆微服务、消息集群或分布式事务。
- 抽象必须减少真实重复或保护重要边界，不能只为了“以后可能用到”。

## 3. 分层与依赖

建议逻辑分层如下：

```text
presentation -> application -> domain
                         ^
infrastructure ----------|
```

### 3.1 Domain

负责实体、值对象、领域服务、策略、状态转换和不变量。

- 不导入 Web 框架、ORM、数据库驱动、文件系统或云 SDK。
- 不读取环境变量。
- 不发送网络请求。
- 不返回 HTTP 状态码或页面对象。

### 3.2 Application

负责用例编排、事务边界、权限协调、仓储接口和外部服务接口。

- 一个公开用例应有明确输入、输出和失败类型。
- 应用层决定操作顺序，领域层决定规则是否合法。
- 不把 ORM 实体直接返回给界面。

### 3.3 Infrastructure

负责数据库、文件存储、邮件、队列、许可证和其他外部系统适配。

- 通过实现应用层定义的接口接入。
- 将外部错误转换为项目定义的错误类型。
- 不能绕过领域规则直接改变关键状态。

### 3.4 Presentation

负责 HTTP、页面、API、序列化和输入格式校验。

- 不直接访问数据库。
- 不承载核心计算和权限规则。
- 返回稳定的用户错误或 API 错误结构。

## 4. 函数和类型

- 公共函数和类型必须有明确职责和文档注释。
- 参数应尽量少且含义明确；一组稳定关联参数可以封装为命令或值对象。
- 避免布尔位置参数，例如 `create_order(data, true, false)`；使用命名参数或明确类型。
- 返回值要稳定。不要在成功时返回对象、失败时返回字符串。
- 可预期业务失败使用明确错误类型或结果类型；程序缺陷不应被当作普通业务失败吞掉。
- 不捕获无法处理的异常。捕获后必须恢复、转换、补充上下文或记录后重新抛出。
- 禁止空的通用异常处理，例如 `except Exception: pass`。

## 5. 类型和数据

- 对公共接口、领域对象、数据传输对象和复杂局部变量使用静态类型。
- 避免把任意字典或任意 JSON 贯穿系统；进入系统后尽早转换为明确类型。
- 可选值必须在类型上表达，并在业务边界处理。
- 枚举或受限值应集中定义，不能散落魔法字符串。
- ID 类型应避免彼此混用；在条件允许时为 TenantId、OrderId 等建立明确类型。

### 5.1 金额

- 金额使用 Decimal 或数据库定点数，禁止使用二进制浮点数。
- 金额必须明确币种、含税口径和舍入规则。
- 舍入只在业务规定的边界发生，不在中间步骤随意舍入。

### 5.2 数量和单位

- 数量、重量、长度和面积必须明确单位。
- 单位转换集中管理并有测试。
- 数据库字段、API 字段和变量名在单位不明显时包含单位，例如 `weight_kg`。

### 5.3 时间

- 系统内部使用带时区时间。
- 保存时使用统一基准，显示时按租户或用户时区转换。
- 日期、时间点和持续时间使用不同类型表达。
- 禁止用格式化字符串代替时间类型参与排序和计算。

## 6. 多租户规则

- 每个租户业务操作都必须从可信身份上下文取得 tenant，不能信任客户端自由提交的 tenant_id。
- 仓储和查询接口必须明确租户范围。
- 租户级唯一约束包含 tenant_id。
- 缓存键、对象存储键、后台任务和导出文件包含租户隔离信息。
- 管理员跨租户操作必须使用单独、显式且可审计的入口。
- 任何新增业务表都要回答“记录属于哪个租户、如何隔离、如何删除和导出”。

## 7. 数据库与事务

- 所有结构变化通过迁移完成。
- 一次用例中需要原子完成的写操作置于同一事务。
- 事务范围应覆盖业务一致性需要，但不在事务中执行缓慢网络调用。
- 查询必须明确排序，不能依赖数据库默认顺序。
- 避免 N+1 查询，并通过测试或性能观察验证优化。
- 大列表使用分页；批量导入使用受控批次和进度记录。
- 不依赖 SQLite 独有的宽松行为；关键查询在 PostgreSQL 上也要验证。
- 原始 SQL 使用参数绑定，禁止字符串拼接用户输入。

## 8. 并发与幂等

- 修改关键记录时考虑重复提交、并发更新和超时重试。
- 对外部导入、付款、库存、订单生成等操作设计幂等键或重复检测。
- 不用“先查再写”代替数据库唯一约束。
- 需要乐观锁时使用版本号或更新时间，并给用户清晰的冲突提示。
- 后台任务必须能识别重复执行，并记录开始、完成和失败状态。

## 9. 配置与依赖

- 配置来自环境或受控配置文件，不写死机器绝对路径。
- 密码、令牌、私钥和连接字符串不得提交到仓库。
- 仓库提供不含秘密的 `.env.example`。
- 新生产依赖必须说明用途、维护状态、许可证、安全影响和替代方案。
- 固定依赖版本并使用锁文件；升级依赖应有测试证据。
- 业务代码不得直接读取散落的环境变量，应通过集中配置对象访问。

## 10. 文件和附件

- 用户文件名与内部存储键分离。
- 文件路径通过存储接口生成，禁止拼接未经验证的用户输入。
- 校验大小、允许类型、内容特征和摘要。
- 下载前重新执行租户与对象权限检查。
- 文件写入采用临时文件加原子替换等方式，避免半写入文件。
- 数据库记录和文件存储之间的失败需要补偿或可恢复状态。

## 11. API 与输入

- 在系统边界校验格式，在领域层校验业务规则。
- 输入 DTO 与输出 DTO 分离，禁止直接暴露内部 ORM 模型。
- API 错误结构稳定，包含可追踪错误码，不泄露堆栈和内部路径。
- 分页、排序和筛选参数必须限制范围。
- 更新接口明确全量替换和部分更新语义。
- 破坏性操作应具备权限、确认、审计和必要的幂等保护。

## 12. 前端代码

- 页面组件负责展示和交互，不复制后端业务规则。
- 状态尽量靠近使用位置；共享状态必须有明确生命周期。
- 表单显示服务端返回的业务错误，同时保留用户已输入内容。
- 加载、空数据、成功、失败和无权限状态都要设计。
- 交互必须考虑键盘操作、标签、对比度和错误提示可访问性。
- 不在浏览器保存长期密钥或授权签发材料。

## 13. 可读性

- 使用提前返回降低嵌套，但不能破坏业务步骤的连续表达。
- 复杂条件提取为有业务含义的谓词。
- 消除魔法数字和魔法字符串，使用命名常量或配置。
- 同一文件保持一致的抽象层级。
- 删除死代码，不用注释保留旧实现；历史由 Git 保存。
- 优化前先测量，优化后保留行为测试并记录原因。

## 14. 自动化质量门槛

技术栈确定后必须配置并在持续集成中执行：

- 自动格式化；
- Lint；
- 静态类型检查；
- 单元测试；
- 集成测试；
- 依赖和安全检查；
- 数据库迁移验证。

具体工具由技术栈 ADR 决定，本规范不提前绑定工具名称。

## 15. 代码评审检查表

- 名称是否表达业务含义？
- 规则是否位于正确层？
- 是否存在不必要的框架或数据库耦合？
- tenant 是否来自可信上下文并贯穿数据访问？
- 金额、单位和时间是否使用正确类型？
- 事务、并发、重复提交和失败恢复是否明确？
- 错误和日志是否安全、可定位？
- 注释是否解释原因并保持准确？
- 测试是否覆盖成功、边界、失败和隔离场景？
- 文档或 ADR 是否需要同步更新？
