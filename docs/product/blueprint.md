# PMS 项目蓝图

状态：草案

## 1. 文档目的

本蓝图定义 PMS 新系统的产品方向、核心边界、演进路线和 Phase 0 完成标准。它不是最终的详细需求说明，也不替代后续 ADR、模块需求和数据字典。

文档中的“已确定原则”约束后续设计；“待决策事项”必须经过评审或 ADR 后才能成为实现依据。

## 2. 背景

现有 PMS 由 Excel、VBA、XLSB 文件型数据库、PDF/图纸目录和部分 Python 打包程序组成。系统已经覆盖大量真实业务，因此具有很高的需求参考价值，但存在路径写死、逻辑分散、多人协作困难、版本不可追踪、数据隔离不足和部署成本高等问题。

新 PMS 不直接在旧工作簿上继续扩建。旧系统整体保存在 `.internal/legacy-pms/`，作为可执行需求文档、迁移数据源和验收基线。

## 3. 产品愿景

建设一套容易部署、容易理解、能够随企业规模成长的生产管理系统：

- 个人可以在一台电脑上快速使用；
- 公司可以在内网由多人共享使用；
- 产品成熟后可以安全地提供给其他企业使用；
- 三种形态共享同一套领域模型和业务代码；
- 业务规则、数据来源和计算过程可以追溯；
- 项目本身可以作为系统化的软件工程学习案例。

## 4. 目标

### 4.1 业务目标

- 统一项目、订单、BOM、采购、生产、库存、付款、发票和报表数据。
- 减少工作簿复制、路径依赖和重复录入。
- 让业务状态、责任人、时间和附件能够关联查询。
- 保留现有系统中已经验证有效的业务流程和操作习惯。
- 为后续多公司使用、授权销售和云端订阅建立基础。

### 4.2 工程目标

- 使用模块化单体降低初期复杂度。
- 业务层与数据库、Web 框架、文件系统和部署形态解耦。
- 使用自动化数据库迁移、测试和静态检查。
- 从第一天建立租户、用户、权限、审计和附件边界。
- 让 SQLite 到 PostgreSQL 的转换主要发生在配置和基础设施层。
- 让关键代码和注释达到学习者可理解、维护者可验证的质量。

## 5. 非目标

第一阶段明确不包含：

- 一开始就拆分微服务；
- 为所有旧工作簿制作一比一的网页复制品；
- 在没有需求映射和验收标准时批量迁移所有历史数据；
- 自建复杂的即时通信、办公套件或通用低代码平台；
- 把授权签发私钥或注册机随客户端发布；
- 让浏览器或多台电脑直接共享打开 SQLite 文件。

## 6. 用户和部署形态

### 6.1 本机版

面向单人或早期试用者。应用在本机启动服务，浏览器访问 localhost，数据存储在 SQLite 和本地附件目录中。

本机版可以简化操作，但内部仍使用默认 tenant、默认管理员和正式数据模型，避免以后补建边界。

### 6.2 内网版

面向公司内部多人协作。应用运行在一台服务机上，用户通过浏览器访问。数据库和附件仅由服务端进程管理。

当出现真实并发写入、稳定运行和集中备份要求时，迁移到 PostgreSQL，不把 SQLite 数据库放在网络共享盘上供多台电脑直接打开。

### 6.3 云端版

面向多家客户。使用域名、HTTPS、PostgreSQL、对象存储、租户隔离、集中监控、备份和订阅权益控制。

云端版与本机、内网版共享业务核心，但可以启用不同的身份、存储、授权和运维适配器。

## 7. 核心业务能力

以下模块来自现有系统的初步归纳，名称和边界仍需通过业务流程梳理确认。

详细来源、证据和优化方向见 [旧系统功能清单](legacy-feature-inventory.md)；带稳定编号的目标能力见 [新系统功能目录](feature-catalog.md)；规则见 [业务规则基线](business-rules.md)。

### 7.1 组织与基础资料

- 企业或租户；
- 用户、成员、角色和权限；
- 客户、供应商和联系人；
- 员工、部门和责任人；
- 物料、分类、单位和价格资料。

### 7.2 项目与销售

- 项目立项和项目档案；
- 销售订单及其变更；
- 客户订单附件；
- 报价和价格核算；
- 项目销售与成本汇总。

### 7.3 BOM 与生产

- BOM 导入、整理和版本；
- 生产请购；
- 生产安排和进度；
- 图纸关联和提取；
- 物料跟踪；
- 外协订单。

### 7.4 采购与库存

- 供应商价格；
- 采购订单；
- 入库录入；
- 出库和领料；
- 库存与项目物料关联。

### 7.5 财务协同

- 付款安排和付款台账；
- 款项报销；
- 销项和进项发票；
- 银行账单与回单；
- 汇票收入、托收、持有和跟踪；
- 凭证和附件导入。

### 7.6 查询与分析

- 跨模块超级查询；
- 项目成本和订单成本；
- 账单、付款和发票台账；
- 可审计的汇总指标和导出。

## 8. 建议的系统边界

初期采用模块化单体。模块之间通过明确的应用服务、领域接口或领域事件协作，禁止跨模块任意访问数据表。

建议的逻辑分层：

```text
Browser / Launcher
        |
Presentation: HTTP, pages, API, input validation
        |
Application: use cases, transactions, authorization orchestration
        |
Domain: entities, value objects, policies, business rules
        |
Infrastructure: SQLite/PostgreSQL, files/object storage, email, licensing
```

依赖方向必须指向业务核心。领域层不能导入 Web 框架、ORM 模型、SQLite 驱动或云存储 SDK。

## 9. 数据设计原则

### 9.1 租户

- 建立 `tenants`、`users`、`memberships`、`roles` 和 `audit_logs` 等基础模型。
- 所有租户业务数据必须包含明确的 `tenant_id`。
- 业务编号的唯一性通常限定在租户内，例如 `UNIQUE (tenant_id, order_number)`。
- 查询、缓存键、任务参数、附件路径和导出文件都必须带租户上下文。
- 测试必须证明用户无法读取或修改其他租户数据。

### 9.2 数据类型

- 金额使用十进制定点类型，记录币种和精度。
- 数量和重量明确单位与换算规则。
- 时间以带时区的时间保存，显示时按用户或租户时区转换。
- 业务编号与数据库主键分离，业务编号可读，主键稳定且不泄露记录数量。
- 状态变化应能追踪操作者、时间和原因。

### 9.3 数据库兼容

- 优先通过 ORM 和迁移表达数据结构。
- 原始 SQL 必须说明必要性，并验证 SQLite 与 PostgreSQL 差异。
- 不依赖 SQLite 宽松类型、隐式日期处理或未明确排序的查询结果。
- 迁移必须可审查、可测试并有恢复策略。

### 9.4 附件

- 数据库保存附件元数据、业务关联、摘要、大小和存储键。
- 二进制内容由存储适配器管理：本机目录、内网目录或对象存储。
- 文件名不作为唯一标识，用户文件名与内部存储键分离。
- 上传和下载都要经过权限校验、类型校验和审计。

## 10. 身份、权限和审计

- 权限判断必须在服务端完成。
- 角色提供常见权限组合，关键动作仍应检查细粒度能力。
- 默认拒绝，只有明确授权才允许执行。
- 审计日志至少记录租户、用户、动作、对象、时间、结果和必要的变更摘要。
- 日志和审计记录不得保存密码、令牌或完整敏感附件内容。

## 11. 授权和商业化

### 11.1 本机或私有化部署

使用数字签名许可证，而不是把可生成授权的注册机交付给客户。许可证可包含客户、版本、期限、最大用户数、功能和可选设备绑定。

签发私钥只存在于独立私有系统；应用只保存公钥并验证签名。需要提前设计续期、换机、宽限期、吊销和离线场景。

### 11.2 云端服务

云端以账户、租户、套餐、订阅和 entitlement 控制功能。传统激活码只适合作为兑换或邀请入口，不作为核心权限机制。

## 12. 质量属性

### 12.1 可理解性

- 关键模块和规则具有教材级文档注释。
- 复杂决策通过 ADR 记录背景与后果。
- 业务术语在代码、界面、文档和数据库中含义一致。

### 12.2 可测试性

- 领域规则可以脱离数据库和 Web 运行单元测试。
- 数据持久化、租户隔离和事务使用集成测试。
- 核心业务流程使用验收测试。
- 数据迁移包含对账和重复执行测试。

### 12.3 可运维性

- 应用提供健康检查、结构化日志和版本信息。
- 数据和附件具备备份、恢复和完整性校验。
- 升级通过版本化迁移完成。
- 桌面、内网和云端分别有可重复的部署步骤。

### 12.4 安全性

- 配置与密钥不进入源码。
- 输入验证、权限验证和租户隔离默认启用。
- 敏感数据最小化收集并在日志中脱敏。
- 上传附件按不可信输入处理。

## 13. 分阶段路线

### Phase 0：蓝图与规范

- 隔离旧系统；
- 建立文档分类和工程规范；
- 梳理术语、角色和功能清单；
- 形成架构、技术栈和数据模型 ADR；
- 选出第一个端到端业务切片；
- 明确第一版验收标准。

### Phase 1：工程基础

- 建立模块化工程骨架；
- 配置格式化、Lint、类型检查和测试；
- 建立数据库迁移、配置、日志和健康检查；
- 实现 tenant、user、membership、role 和 audit 基础能力；
- 完成本机启动器和 localhost 访问。

### Phase 2：本机最小可用版本

- 选择一个高价值、边界清晰的业务闭环；
- 完成录入、查询、状态变化、附件和导出；
- 从旧系统迁移最小数据集；
- 与旧系统逐项验收。

### Phase 3：内网多人版

- 正式身份认证和权限矩阵；
- PostgreSQL 迁移评估或实施；
- 服务化部署、集中备份和恢复演练；
- 并发、事务和审计测试。

### Phase 4：业务覆盖扩展

- 按价值和依赖顺序迁移其他模块；
- 建立跨模块报表和统一查询；
- 逐步停止对应旧工作簿的新增录入。

### Phase 5：商业云端版

- 多租户安全复审；
- 云端部署、对象存储、监控和灾备；
- 套餐、订阅、许可证和客户生命周期；
- 数据导入、导出和租户迁移能力。

## 15. 待决策事项

- 后端框架和版本；
- 前端采用服务端渲染、渐进增强还是独立 SPA；
- ORM、迁移工具和依赖管理工具；
- 本机启动器和桌面打包形式；
- 用户认证与会话方案；
- 内网阶段切换 PostgreSQL 的明确触发条件；
- 云端租户隔离采用共享表、独立 schema 还是其他方式；
- 附件本机目录结构和云端对象存储供应商；
- 第一个端到端业务切片；
- 旧系统数据保留期限与脱敏策略；
- 私有化许可证的设备绑定和离线策略。

## 16. 第一版候选验收标准

以下是项目级候选标准，待选定首个业务切片后细化：

- 新用户可以在干净电脑上按文档启动本机版；
- 服务只监听本机地址，浏览器可以自动打开；
- 初始化默认租户和管理员过程可重复；
- 关键业务流程不依赖 `.internal/legacy-pms/`；
- 数据重启后保持一致，数据库迁移可从空库执行；
- 关键领域规则、持久化和权限边界有自动化测试；
- 租户 A 无法读取、猜测或修改租户 B 的数据；
- 金额、时间、状态和附件行为符合文档定义；
- 备份能够在另一空目录恢复并通过完整性检查；
- 用户能够将首个业务闭环与旧系统结果进行人工对照。
