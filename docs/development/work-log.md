## 2026-08-24：修复 F-011 Linux 连续重启端口误判

### 现象与定位

- GitHub `Quality` 运行 `32649827681` 对提交 `c974803` 的格式、Lint、mypy 和 127 个测试均
  通过，但“全新本机安装烟雾”失败，后续 PostgreSQL 和审计步骤因此跳过。
- 公开 API 将失败定位到恢复目录的第二次 `launch_local`。该步骤刚停止第一个处理过 ready
  请求的 Uvicorn，又立即在同一端口启动恢复实例。
- Linux 会暂时保留已关闭连接的 `TIME_WAIT`；Uvicorn/asyncio 监听器允许安全
  `SO_REUSEADDR`，而启动器预检 socket 未采用相同选项，因而可能在 Uvicorn 本可重启时误报
  端口占用。Windows 本地连续重启未复现，属于平台行为差异。

### 修复

- 端口预检在 bind 前设置 `SO_REUSEADDR`，只复用刚关闭的本地监听地址，不绕过仍在监听的真实
  占用；既有“活动 listener 必须拒绝”测试继续保留。
- 新增调用顺序回归测试，确保地址复用选项先于 bind 生效。

### 验证

- Ruff format、Ruff Lint、严格 mypy、Django checks、迁移漂移和 uv 锁文件通过。
- 128 个 pytest 全部通过，分支覆盖率 85.08%；pip-audit 未发现已知漏洞。

- 为同一数据目录建立跨平台操作系统排他锁：Windows 使用 byte-range lock，POSIX 使用
  `flock`；锁文件只记录不含路径和秘密的诊断元数据，进程退出后内核自动释放。
- 在独立线程轮询 loopback ready，成功后默认浏览器只打开一次；超时请求 Uvicorn 安全退出，

  启动器复验恢复数据目录。

### 判断

- 采用同进程 Uvicorn 而不是父启动器派生子进程，避免父进程被关闭后遗留孤儿服务和锁失配。
- 互斥事实由内核锁而非锁文件存在性表达；锁文件故意保留，释放后删除会在 POSIX 引入 inode
  竞态并允许两个实例同时持有不同文件。
- `--no-browser` 只服务 CI 和无图形环境，不能绕过迁移、初始化、端口、锁或 ready 检查。
- F-011 是源码级跨平台入口；桌面快捷方式、安装包、系统托盘和内置 Python 运行时仍属后续
